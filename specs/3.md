## Problem

Discord's RPC never exposes audio, so Orbolay has none. To transcribe, we must capture two streams
ourselves: the local microphone (what *you* say) and the audio Discord plays (what *others* say).
This spec creates the RTT crate and does the Linux implementation first, since that's the
development platform.

### Overview

This spec gets audio into the app. **Proposal** introduces the new `orbolay-rtt` crate with one
interface for audio sources, and two Linux implementations: microphone and "what Discord plays"
(loopback). **Design** explains the shared clock that later lets speaker attribution line audio up
with Discord's speaking events. The main uncertainty, in **Open Decisions** and **Risks**, is
whether we can capture only Discord rather than all system sound.

## Proposal

- New workspace crate `crates/orbolay-rtt`, compiled only with the root `rtt` feature.
- `AudioSource` trait that yields timestamped `f32` mono frames on a `flume` channel. Timestamps use
  a monotonic clock shared with the speaking timeline (see `rtt-speaker-attribution`).
- `MicSource` via `cpal`, using the default input device or a configured `rttMicDevice`.
- `LoopbackSource` on Linux: open the PulseAudio/PipeWire **monitor** of the default sink (or a
  configured `rttLoopbackDevice`). Optionally target only Discord's sink-input if feasible.
- Resampler to 16 kHz mono (`rubato`), so downstream STT has a single format.
- `rtt-capture-test` dev binary/example that records 10 s of each source to WAV for inspection.

## Out of Scope

- Windows/macOS loopback. That's `rtt-capture-windows-macos`. Mic capture via `cpal` is expected to
  work cross-platform already, but it's only *verified* on Linux here.
- Echo cancellation between mic and loopback. Discord already applies its own processing to the
  mic, and headset users have little bleed. Revisit only if testing shows duplicate captions.
- The CI half of source task 2.2 (Linux build deps for `--features rtt` in
  `.github/workflows/check.yml`). A workflow edit can only be proven by a CI run, and whether upstream
  wants the job is an open epic decision, so it moved to spec 11 in epic `rtt-human` (id 7).

## Design

- `cpal` for the mic: it's mature, cross-platform, and already the de-facto Rust choice.
- Linux loopback: PipeWire exposes PulseAudio-compatible monitor sources, so one PulseAudio-API
  implementation covers both servers. The approach is either `cpal` (ALSA `pulse` device with
  `PULSE_SOURCE=<sink>.monitor`) or `libpulse-simple-binding` with an explicit monitor source. The
  choice is made in task 1.2 by spike, preferring the one that needs no extra system library.
- Each source runs on its own thread and never blocks the audio callback: the callback copies into a
  lock-free ring/`flume` and returns, and resampling happens on the consumer side.
- Timestamps come from `std::time::Instant` relative to a pipeline epoch created once at RTT start.
  The speaking timeline uses the same epoch, which makes attribution a simple interval overlap.

## Alternatives Considered

- Native `pipewire` crate (pipewire-rs). Rejected for now: heavier bindgen/build dependency and
  PipeWire-only (no plain PulseAudio). Reconsider if per-app capture of only Discord's stream is wanted.

## Open Decisions

- Capture only Discord's output vs. the whole system mix. Whole mix is simplest but transcribes
  game/music audio too. Decided in task 1.3 by checking whether Discord's sink-input can be
  isolated (via a null-sink + loopback or a pulse sink-input monitor). If not cheaply possible,
  ship the whole mix with VAD and document it.

## Risks

- Game audio and music in the loopback produce garbage captions. Mitigation: VAD in `rtt-stt-engine`,
  per-app capture if feasible (open decision), and a "loopback off" option (mic-only captions).
- Audio callback starvation causes dropouts. Mitigation: do no work in the callback, and use bounded
  channels that drop the oldest data rather than block.
