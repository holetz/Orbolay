## Problem

Spec 22 (PR #8, merge e4125f6) bounds the model download with `timeout_connect` 15 s, `timeout_recv_response` 30 s and `timeout_recv_body` 30 min (`crates/orbolay-rtt/src/stt/models.rs:129-131`); the comment at `:28` says ureq has no per-read timeout. Consequence: a server that stops sending mid-body leaves the "Download Speech Model" action hung for up to 30 minutes with no progress and no error, which is what spec 22's Problem asked to prevent. Fix: a per-chunk read deadline (e.g. a watchdog on bytes received, or ureq's per-read socket timeout if the version exposes one) with a test using a local stalled server.

## Proposal

- A model download whose body stops arriving for longer than a stall deadline (30 s) aborts with an error naming the stall, instead of hanging up to 30 minutes.
- The 30-minute whole-body cap stays as the outer bound.
- The stall deadline is a parameter of the fetch path, so tests use a sub-second value.
- A regression test with a loopback TCP server (headers plus some bytes, then silence) proves the abort; it failed on the pre-fix code.

## Out of Scope

- Retrying or resuming a stalled download: the user re-triggers the button.
- Changing the connect (15 s) and response (30 s) timeouts, or adding a UI progress indicator.
- Killing the blocked reader thread: ureq offers no read cancellation; it ends at the body cap or when the peer closes.

## Impact

### Standards this spec will write into docs/standards/

- none — a private timeout detail, no standard.

### Product code this spec expects to touch

- `crates/orbolay-rtt/src/stt/models.rs` — `fetch`, the timeout constants and the comment at line 28.

## Validation

- `cargo test -p orbolay-rtt stalled_download` passes after the fix; against the pre-fix code the same test failed (the fetch was still blocked when the test's own 5 s guard expired).
- Full gate from `.claude/CLAUDE.md`, plus the `--features rtt` variants and `cargo test -p orbolay-rtt --features capture`, exits 0.

## Design

- **Watchdog by channel.** `fetch` reads the body in a worker thread and sends chunks over a bounded channel; the caller writes them to the file using `recv_timeout(stall)`. A timeout returns `Err("download stalled: no data for Ns")`, and the partial file is removed by `download` as for any error. Rule: a read deadline lives in the consumer, so it holds even when the blocking read never returns.
- **Injectable.** `fetch(url, dest, stall: Duration)`; `download` passes `STALL_TIMEOUT` (30 s). The worker thread is left to end on its own when the peer closes or the body cap fires.
- ureq 3 `Agent` config has no per-read timeout (the existing comment), so a socket-level option is not available.

## Alternatives Considered

- Per-read socket timeout via a custom connector or transport: needs a ureq transport implementation, far larger for the same effect.
- Lowering `timeout_recv_body`: would cut legitimate slow but progressing downloads of the 490 MB model.

## Open Decisions

- none — the 30 s value mirrors the response timeout; adjust if field reports show slow links.

## Risks

- ACCEPTED — a stalled worker thread and socket linger until the peer closes or the 30-minute cap fires; one per aborted attempt, user-triggered and rare.
- A stall deadline too short for a very slow link: 30 s with zero bytes is far past normal jitter.
