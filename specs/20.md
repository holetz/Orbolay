## Problem

Reproduced by the epic 13 review: frames stamped 0 ms and 5000 ms → `[4] input ts 0ms,5000ms -> output ts 0ns, 100ms`. Output time is first frame + samples emitted (`crates/orbolay-rtt/src/audio/resample.rs:50, 124-127`), while a full queue silently drops oldest frames (`crates/orbolay-rtt/src/audio/mod.rs:91-98`). Consequence: after any drop every later segment is stamped early by the dropped duration, so loopback attribution (`crates/orbolay-rtt/src/pipeline.rs:224-230`) matches the wrong Discord speaker and caption times are wrong.

## Proposal

- After a gap in input timestamps, resampler output timestamps follow the input timestamps again instead of lagging by the dropped duration.
- The behaviour is covered by a regression test that fails on the pre-fix code.

## Out of Scope

- Changing `FrameSender` drop policy in `audio/mod.rs`: dropping oldest is intended; only the stamping was wrong.
- Editing `pipeline.rs`: its attribution reads timestamps correctly once they are correct.

## Impact

### Product code this spec expects to touch

- `crates/orbolay-rtt/src/audio/resample.rs` — gap detection and re-origin

## Validation

- `cargo test -p orbolay-rtt resample` passes, including a new test feeding frames stamped 0 ms and 5000 ms that expects the second output stamped at 5000 ms.
- The new test fails on the pre-fix code.
- Full gate per `.claude/CLAUDE.md`.

## Design

- Track the expected end of the previous input frame (`timestamp + duration`). When a frame starts more than a tolerance (50 ms, assumption: above capture jitter) after it, the stream is discontinuous: the buffered sub-chunk tail (under 1024 input frames) is discarded and the resampler re-origins on the new frame's timestamp.
- Rule: output timestamps are anchored to input timestamps at every discontinuity, never to a running sample count alone.
- Assumption: dropped-frame gaps are always forward jumps; backwards timestamps are left unchanged.

### Mapa de dependências

- `audio/resample.rs` `MonoResampler` is used only by `pipeline.rs:179,188` (process only); signature unchanged, so nothing breaks.

## Alternatives Considered

- Pad the gap with silence: unbounded output for long gaps and pointless STT work; rejected.
- Flush the old tail before re-origin: needs process to return two frames, changing the `pipeline.rs` contract; rejected for ownership.

## Open Decisions

- none — the tolerance is an assumption named in Design, adjustable in the constant.

## Risks

- Up to about 21 ms of audio before a gap is discarded. ACCEPTED — the audio preceding a drop is already discontinuous.

Shipped: MonoResampler now tracks where the previous input frame ended and, when a frame starts more than 50 ms past that (dropped frames), resets and re-anchors the output origin on the new frame, so output timestamps follow input gaps. Regression test `output_timestamps_re_anchor_after_an_input_gap` covers 16 kHz and 48 kHz. Left out: nothing.

Pre-fix proof: with the `|| gap` condition temporarily removed from the working tree (branch and history untouched), `cargo test -p orbolay-rtt --features capture output_timestamps_re_anchor_after_an_input_gap` FAILED, exit 101 ("rate 16000: output stamped 120ms, expected >= 5s"); restored, it passes.
