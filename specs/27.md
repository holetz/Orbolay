## Problem

Reproduced by the epic 24 review (harness `target/quenching/review2/leak`, `fetch` copied from `models.rs`, ureq 3.4.2, loopback server stalling mid-body): `before: threads=2 sockets=2` → `after stalled fetch #5: threads=7 sockets=12` → `after waiting 12s (body cap 1800s): threads=7 sockets=12`; with a 3 s body cap all client sockets were released. The reader thread spawned at `crates/orbolay-rtt/src/stt/models.rs:142` is bounded only by `BODY_TIMEOUT` (`:31`, 30 min) after spec 25's stall deadline gives up on it. Consequence: each retry against a stalled server keeps one thread and one TCP socket for up to 30 minutes. Bounded, no `.part` handle held (`open_fds_on_part=0`), hence low.

## Proposal

- A download whose body stalls past the stall deadline releases its reader thread and TCP socket within seconds, not up to `BODY_TIMEOUT` (30 min).
- The 30-minute whole-body cap and the 30 s stall deadline in `fetch` keep their current behaviour and error text (`download stalled: ...`).
- A loopback regression test proves the reader thread (and so its socket) ends shortly after the stall, and fails against the pre-fix code.

## Out of Scope

- Changing `STALL_TIMEOUT` or `BODY_TIMEOUT` values: not the defect.
- Resuming or retrying downloads (Range requests): a feature, not a leak fix.
- Other ureq callers (`orbolay-transport`, `orbolay-ui`): the reproduction is only the model download.

## Design

- ureq 3 has no per-read timeout, so the reader's blocking read is bounded only by the body cap. Rule: wrap ureq's `DefaultConnector` in a connector whose transport clamps every `await_input` timeout to the stall window. A read that gets no bytes for that window then returns a timeout error, the reader thread exits and drops the socket. The 30-min cap still applies because the clamp is `min(remaining, stall)`.
- `fetch` builds the agent with `Agent::with_parts(config, ClampConnector, DefaultResolver)`; the clamp equals the `stall` argument so the test can use a short window.
- Assumption: ureq's TLS layers pass the `NextTimeout` through to the TCP transport unchanged (read in ureq 3.4.2 source).

## Alternatives Considered

- Keep a socket clone and `shutdown` it on stall: ureq exposes no handle to the stream; would need re-implementing the TCP/TLS connector chain.
- Lower `BODY_TIMEOUT`: breaks slow but progressing downloads of a ~490 MB model.
- Per-chunk Range-resume loop: much larger change.

## Open Decisions

- none — the approach is settled by the evidence above.

## Risks

- ureq's `unversioned` transport API may change on upgrade: ACCEPTED — the dependency is pinned by Cargo.lock and a regression test covers it.
- The clamp also applies to the response-header read: ACCEPTED — that is already bounded at 30 s by `RESPONSE_TIMEOUT`, equal to `STALL_TIMEOUT`.
