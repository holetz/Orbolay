## Problem

Orbolay ships for Windows, macOS and Linux, and most of its users are on Windows. An upstream PR
that only works on Linux would be a hard sell. Loopback capture is the only platform-specific
part of RTT.

### Overview

This spec makes captions work beyond Linux. **Proposal** adds the Windows and macOS versions of
"capture what Discord plays", preferring each OS's ability to record a single app so game sound
isn't captioned. The rest of the pipeline is untouched. The main risks are testing without local
hardware and macOS permissions, covered in **Risks**.

## Proposal

- `LoopbackSource` for Windows via WASAPI loopback on the default render device (through `cpal`'s
  loopback support if adequate, else the `windows` crate already in the workspace). Use process
  loopback (`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, Win10 2004+) to capture only
  Discord's process tree when available.
- `LoopbackSource` for macOS via ScreenCaptureKit audio capture (macOS 13+), filtered to the
  Discord app. Handle the Screen Recording permission prompt with a clear status in the RTT settings.
- Windows/macOS code verified from Linux with `cargo check --target` (see ## Validation). *(Port
  note: the source bullet "Builds of `--features rtt` verified on all three CI targets (whisper.cpp
  with MSVC and Apple clang)" is a CI workflow change and moved to spec 11 in epic `rtt-human`.)*
- Platform-specific settings `#[cfg]`-gated, as CONTRIBUTING.md requires.

## Out of Scope

- macOS < 13 (no ScreenCaptureKit audio). RTT shows "mic only" there.
- Virtual audio driver approaches (BlackHole, VB-Cable). Users can still select such a device
  manually via `rttLoopbackDevice`.
- CI jobs building `--features rtt` on all three OS (source task 3.1): moved to spec 11.
- Manual runs on Windows 11 and macOS 14 hardware: moved to spec 12 (validation matrix).

## Validation

- **Buildability condition.** A Linux-only autonomous agent can build this spec only because every
  Windows/macOS task is checked with `cargo check --target` on Linux (targets
  `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, installed with `rustup target add`; only
  `x86_64-unknown-linux-gnu` is installed today). If a target cannot be checked on Linux (a build
  script needs MSVC, the macOS SDK or Swift), the affected task is marked blocked (`[!]`) with that
  reason and handed to epic `rtt-human`. It is never marked done on any other evidence.
- `cargo fmt --check && cargo clippy --workspace --features rtt -- -D warnings && cargo test --workspace --features rtt` passes on Linux.
- `cargo check -p orbolay-rtt --target x86_64-pc-windows-msvc` and
  `cargo clippy -p orbolay-rtt --target x86_64-pc-windows-msvc -- -D warnings` pass.
- `cargo check -p orbolay-rtt --target aarch64-apple-darwin` and
  `cargo check -p orbolay-ui --target aarch64-apple-darwin` pass.
- *(Port note: "passes on Windows, macOS and Linux CI runners" moved to spec 11; "Manual on Windows
  11: Discord call captions work, and game audio isn't transcribed when process loopback is
  available" and "Manual on macOS 14 (Apple silicon): permission prompt appears once, then captions
  work" moved to spec 12.)*

## Design

- Prefer process-scoped capture on both OSes (Windows process loopback, ScreenCaptureKit app filter).
  It solves the "game audio becomes captions" problem that Linux may only solve partially.
- Fall back to whole-system loopback on older Windows, and to mic-only with an explanatory status
  on old macOS.

## Alternatives Considered

- Requiring a virtual audio device on all platforms. Rejected: poor UX and a support burden for
  upstream.

## Open Decisions

- Whether `cpal`'s WASAPI loopback can target a process, or raw `windows` crate calls are needed.
  Decided by spike in task 1.1.
- Which Rust ScreenCaptureKit binding to use (`screencapturekit` crate vs. hand-written
  `objc2` bindings). Decided by spike in task 2.1, based on maintenance status and build impact.
  *(Port addition: "can it be `cargo check`ed from Linux" is now a deciding criterion.)*
- *(Port addition)* How to cross-check when a native build script (e.g. `whisper-rs-sys`'s
  cmake/bindgen) breaks `cargo check --target` on Linux. Decided in task 1.2 by running the check;
  if it fails for a reason outside this spec's files, record it in ## Discoveries and ask the human
  before restructuring `orbolay-rtt` features.

## Risks

- No local Windows/macOS hardware for manual tests. Mitigation: CI builds, plus a call for testers
  in the upstream issue. A VM is fine for Windows.
- macOS notarization/entitlements for screen capture in the bundled `.app`. Mitigation: check
  `build.yml` bundling, and add the usage description key to Info.plist via cargo-bundle metadata.
- *(Port addition)* The macOS target may not be checkable from Linux at all (SDK- or Swift-dependent
  build scripts in the audio or ScreenCaptureKit bindings). Mitigation: prefer bindings without such
  build scripts in the 2.1 spike; otherwise block 2.2 and hand it to `rtt-human`.

## Handoff
