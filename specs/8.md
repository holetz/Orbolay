## Problem

The RTT epic (id 1) wants direction agreed with upstream before the bulk of the work, using a
concrete mock-up of the caption panel. Both steps need a human: the screenshot needs a display and
a judgement of what looks right, and `.claude/CLAUDE.md` forbids creating issues on
`SpikeHD/Orbolay` from automation. Gathered here from `rtt-transcript-panel` task 3.2 and epic tasks
1.1 and 1.2 (source `specs/plans/rtt-transcript-panel.md`, `specs/plans/rtt-epic.md`).

## Proposal

- Run the panel demo (`cargo run --features rtt -- --rtt-demo`), check it visually and capture a
  screenshot or short GIF.
- Open a feature-request issue on `SpikeHD/Orbolay` describing RTT as an optional, feature-flagged,
  local-only addition, with the mock-up, and ask about the CI job and model download.
- Record the maintainer's answer and amend the child specs if the requested shape differs.

## Out of Scope

- Any product code. The demo itself is built by spec 2.
- The CI job (spec 11) and the PR (spec 12), which follow from the answer recorded here.

## Impact

### Product code this spec expects to touch

- none — evidence goes to this spec's ## Discoveries and amendments go to specs 2 to 6 via
  `/specs:develop`.

## Validation

- `cargo run --features rtt -- --rtt-demo` shows scrolling, labelled, fading captions, and the
  screenshot/GIF is attached to the upstream issue (moved from spec 2's ## Validation).
- The issue URL is recorded in ## Discoveries.
- The maintainer's answer is summarized in ## Discoveries, and the child specs are updated via
  `/specs:develop` when the requested shape differs.

## Design

- The issue frames RTT the way epic 1 designs it: Cargo feature `rtt` off by default, runtime
  `rttEnabled` off by default, local-only processing, nothing written to disk.
- Use the same issue to settle three open decisions: whether the PR should add a `--features rtt`
  CI job (epic 1), model distribution (download vs. user-supplied path; `rtt-stt-engine`), and the
  default panel position (spec 2, settled with screenshots).

## Alternatives Considered

- Skipping the issue and opening the PR directly. Rejected: CONTRIBUTING.md asks for an issue first,
  and the epic's main risk is upstream declining after the work is done.
- A sidecar prototype (Python + faster-whisper) to validate latency and UX before the issue (epic 1
  Alternatives). Optional, at the human's discretion; not required by this spec.

## Open Decisions

- Will upstream accept RTT, and in what shape? Decided by the maintainer's answer. Accept as
  optional feature → proceed as specified; accept with changes → amend specs via `/specs:develop`;
  decline → keep `develop` as the fork's product branch and skip spec 12.
- Whether specs 3 to 6 wait for this answer (epic 1 Risks: "open the issue before building section
  2+"). The store cannot express a cross-epic edge; the human decides.

## Risks

- Upstream rejects or ignores the proposal. Mitigation: the fork is useful on its own; the
  long-lived-fork fallback stays open (GPL-3.0).

## Handoff

- Runs after spec 2 (`rtt-transcript-panel`, epic `rtt`) is merged into `develop`: the demo flag
  must exist.
- Upstream: https://github.com/SpikeHD/Orbolay. Never create the issue from automation.
